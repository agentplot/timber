title: Roadmap
description: The three phases that build timber, what each delivers as an installed binary, what each is done by, and the six bolts of phase 1 that v0.6.0 holds.
---

The statement is written and ruled, and phase 1's six bolts have
landed: v0.6.0 is the binary that holds them. timber is built in
three phases, each a few bolts, and each bolt after the first ends in
a binary installed the way sluice is, `nix profile install
github:boomdrivedev/timber`, a release tarball or `cargo install`, that
does something a person uses the same day. A phase is done by a check
or an observation, never by a list ticked by hand. Nothing hosted is
built until people running the open-source tool ask for it.

## Phase 1 · Useful on the family's own repositories

**Goal.** Build once, promote forever, every day, on sluice, timber,
crew and the blueprints: a landing becomes a version in a store the
owner holds, a channel moves only by a signed promotion, and a checkout
installs what the channel names.

**Bolt 1 · the core.** Every seam's trait and the types they pass, the
in-memory fakes, the conformance suite with each scenario citing its
clauses; the policy file read at the landed revision, components and
the version rule; claims and envelopes; `timber publish`, `status`
and `verify` running end to end over the fakes. Built by one agent in
sequence, so every later bolt codes against it.\
*Done when* the conformance suite passes over the fakes and a publish
runs against an in-memory store in the tests.

**Bolt 2 · publish, on one laptop.** The store as an OCI layout on
disk; moon as the build and sluice or a plain branch as the landing; a
host key as the signer; the host's bindings beside the landing's; a
version offered with provenance and sluice's verdicts attached, its
answer machine-readable.\
*Done when* a landing on one of the family's repositories is published
from a laptop into a layout on disk, and a second machine verifies the
index and every referrer from a copy of that layout.\
*Landed:* the layout on disk, moon, sluice and the plain branch, the
host key, and the laptop: the host's bindings file, the policy file's
signers and audiences, and the file and image projections' pack, so the
installed binary publishes a sluice landing into a layout and a second
machine verifies a copy of it.

**Bolt 3 · the cache, on a registry.** The OCI registry store with
ECR's referrer fallback, and a layout synced to it; the cache namespace
in the same store, where a cache entry is never an artifact; a step
after a landing pushing the archives the landing's build left; `timber
sync` filling moon's outputs directory on any host with the entries
whose task hashes the landing's verdicts name, shared by every checkout
on the host.\
*Done when* a task that passed on one host replays from the store on
another, and a checkout's first build of a landed revision runs nothing
the landing already ran.\
*Landed:* the OCI registry store, held to the store scenarios against
zot in the gate and against ECR by hand, with the referrers tag where a
registry answers no referrers API, and a version copied from a layout
into a registry with every attestation beside its digest; the cache
namespace, where a cache entry is never an artifact, and `timber sync`
rendering moon's outputs directory, shared by every checkout on the
host, from the entries the landing's verdicts name; and `timber push`
after a landing, writing the entries the landing's build left on its
host, with `timber rebuild` making the host's record of what it
published again from the store and git.

**Bolt 4 · the gate and the channels.** A key in a key service as the
signer; the gate accepting under the policy and `beta` following each
publish; `timber promote` appending a signed claim to the chain in a
git ref the gate pushes, the same claim attached in the store, a
rollback a promotion back; `timber status` reading channels and the
chain on any machine.\
*Done when* a promotion made on one machine is read on another from the
ledger alone, a promotion from a stale predecessor is refused naming the
head, and a rollback is a promotion to an older version.\
*Landed:* the key in AWS KMS as the signer; the gate accepting under the
policy, with `beta` following each publish; and the ledger and
promotion: `timber promote` judging a version under the channel's
policy and its binding, the git ref and the store as the ledger, a
rollback a promotion back, and a channel read on a second machine from
the git ref alone; and status on any machine: `timber status` showing
every channel the policy declares at its version, with the chain that
put it there, read from the ledger on a machine that never published,
and the host's one serving process showing every repository it knows
on one page and each whole on a page of its own.

**Bolt 5 · sync and serve.** Consumer layouts under a policy: npm and
Cargo rendered and served by one process per host at a fixed port; the
Claude Code plugin whose hook refuses `npm publish` and names timber's;
the herdr pane of channels and environments.\
*Done when* `npm install` and `cargo build` in a family repository
resolve a package only from a version whose claims satisfy the policy,
and a version that fails it is refused with the reason.\
*Landed:* render under a policy, `timber sync` holding in each layout
only the versions a checkout's lockfiles pin, and every family package
they require, whose claims the layout's policy admits, and refusing the
rest with the reason; npm packed with npm's own packager and Cargo's
crates with Cargo's, each rendered and answered by the host's one
serving process at one fixed address with the repository in the path,
Cargo's as a sparse registry; every artifact named in the store by its
ecosystem, name and version, so a consumer finds what its lockfile pins
by those alone; a version's notes rendered from the history that
derives it and carried as an artifact of the version, a channel's
changelog read from them, and the gate judging each artifact by its
kind; a pool's check job pushing what its run left before the landing,
and a publish taking its outputs from the cache entries the landing's
verdicts name; the Claude Code plugin, whose hook refuses an
ecosystem's own publish command and names `timber publish`; and the
herdr plugin, a pane of every repository the host knows and each one
whole, read from the host's one serving process.

**Bolt 6 · the Nix fleet, pushed.** A Nix binary cache as a target, a
version's closures pushed to the fleet's cache; one machine of a clan
fleet converged by `timber apply` from the host that holds its key, its
report a claim beside the version; a channel that comes after an
environment moving only to what that environment last reported.\
*Done when* swancloud's machines are deployed by `timber apply` from
the deployer's host, each on a channel moved by the gate or by a
person's yes, and swancloud's own deployer retires.\
*Landed:* the policy's environments, each bound to a target by its
profile, and `timber apply` judging the claims the channel's policy
requires of its head before the target is handed the version; a Nix
closure as one artifact naming its roots, its store paths the fleet's
cache's, which answers the statement's last open question; the Nix
cache target, pushing a version's closures with attic from the host
that built them, so a closure built on one host is realised on another
from the cache alone; the clan push profile, checking the machine's
toplevel at the version's revision against the closure's one root,
realising it from substituters alone and switching the machine with one
`clan machines update`, then leaving a marker on the machine and a
report claim the host signs beside the version; a channel an `after`
makes moved by the gate to what every environment it names last
reported; and `timber status` and the pages showing every environment,
what it should run, what it runs from its reports in the store, and the
notes of every version between the two.

## Phase 2 · Open to others

**Goal.** Anyone with a git repository, a registry and a key runs it,
and every seam has the profiles the statement names.

- The remaining projections: Maven, Python, Go, NuGet, and a file and
  an image as rendered layouts.
- Targets that push: a package registry, a static site, a
  CloudFormation stack or StackSet, a function; the environment that
  waits for an approver, whose approval is a promotion.
- The profiles a control plane binds, generic and held to the
  conformance suite: the ledger as a database table with conditional
  writes (C.15), the roster a target answers (126), the pool target
  (C.12) and the CloudFormation template set projection (C.11).
- Keyless signing against a public or private issuer; the verifier's
  independent rebuild as a claim.
- The conformance suite published, so a profile anyone writes is held
  to Parts A and B.
- Guides: bring your own registry, a key in a key service, the policy
  file, each ecosystem's packager setup.

*Done when* a repository outside the family publishes, promotes and
syncs with no change to timber, and its operator wrote no code.

## Phase 3 · 1.0

**Goal.** The formats and the command line freeze, and an environment is
told nothing but its channel.

- Targets that pull: Kubernetes through Flux or Argo with a status
  watcher, a Nix fleet through Clan.
- Two signatures before `stable` moves, the second an independent
  rebuild with the shared cache off; a reference self-hosted Sigstore.
- The Boomdrive plugin, whose adapter prints a capture for each publish
  and each refusal.
- A control plane that keeps its own tables and fans out to many
  instances, running end to end on the table ledger and the pool
  target.

*Done when* a `stable` promotion is refused without the second signature
and accepted with it, and converges a production environment that
waited for a person.

## After timber

The formats and the command line stay frozen. Anything hosted, a
private certificate authority tied to the user's identity provider, a
transparency log, countersigning, comes only when people running the
open-source tool ask for it, and holds none of their artifacts and none
of their ledger.
