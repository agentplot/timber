# timber's flake gives a module that writes the host's bindings file and nothing else

Status: accepted on the brief of the change timber-publishes-its-own-module, 2026-11-14, whose ask is clause 118 as amended at `boomdrivedev/blueprints` 573ec1a, on the branch `design/timber-deploys-dash0-dashboards`, in its words: "On nix-darwin and NixOS, timber's own module, `services.timber`, writes the file from `services.timber.settings`, one option per key, each named as the file names it, so a host names a credential as `services.timber.settings.credentials.<name> = "<path>"`. Boomdrive's set takes that module from timber's flake and writes no file of timber's." How timber carries it out below is the construct stage's own, made on 2026-11-14 within records 0013 and 0033 and the rules, each choice cheap to change.
Sources: statement clauses 45, 64, 92, 114 and 118 as amended at `boomdrivedev/blueprints` 573ec1a, C.1, C.2, C.5 to C.8, C.13, C.14 and C.16; agentplot/boomdrive record 0023 as amended on 2026-11-13, and its rules core.18 and core.46; sluice's record 0098 and its `nix/` at `boomdrivedev/sluice` 7ce112b4, itself Boomdrive's at 3f428cf; records 0013, 0021, 0031 and 0033; rules core.1, core.21, core.25, core.26, core.36, core.38, core.54 and core.74.

## Context and problem statement

timber reads the host's bindings from `~/.config/timber/config.toml`, or under `$XDG_CONFIG_HOME` where it is set, at every command and at each request the serving process binds for, and never writes it (118; records 0013, 0021). A table the file leaves out binds its given one, and a table it names binds exactly what it names.

timber's flake built the package alone. A host configured by Nix that wanted a registry, a key service, a shared ledger or, with record 0033, a target's credential wrote the file by its own means, outside anything of timber's, and Boomdrive's set carried timber's package by an option of its own until timber gave a module (boomdrive record 0023). sluice and Flume already give theirs, in one shape: options named as the tool's file names them, rendered at evaluation, linked for the user who runs the tool, and checked offline against no store by a moon project `nix`. Boomdrive rules core.18 and core.46: each tool's own flake gives the module that writes the tool's own file, and no module writes another tool's.

## Considered options

1. timber's flake gives `services.timber` in the family's shape, its options the file's own tables and keys.
2. Options of the module's own, one per seam naming its profile, `store.profile = "layout"` beside `store.path`.
3. A home-manager module.
4. Boomdrive's set writing timber's file, as it carried timber's package.

## Decision outcome

Option 1, sluice's shape (its record 0098) for timber's file.

- **The modules, the systems and the layout.** `flake.nix` gives `darwinModules.timber` and `nixosModules.timber`, each also `default`, each `{ _file; key = "github:boomdrivedev/timber#<platform>Modules.timber"; imports = [ (import file { inherit packages; }) ]; }`, so a system that imports the module itself and through Boomdrive's declares `services.timber` once. The key names `boomdrivedev`, as record 0032 has timber's addresses. Both import `nix/modules/options.nix`, given the flake's own `packages`. Everything of the flake but `flake.nix` and `flake.lock` is under `nix/`, and `flake.nix` keeps the two lines `root:release` reads (record 0031, core.74). The flake gives aarch64-darwin, aarch64-linux and x86_64-linux, since its nixpkgs refuses x86_64-darwin since 26.11 and no release builds it. The tests take nix-darwin as an input of the flake following its nixpkgs, locked at sluice's revision ff0e21a4, which evaluates against timber's nixpkgs; the modules import nothing of it.
- **`services.timber`'s options, named as the file names them.** `enable`; `package`, the flake's package for the host's system by default, a system the flake gives none for failing evaluation naming the systems it gives, and `null` installing none; `user`, on NixOS alone, with no default; `text`, internal and read-only, the file's text; and `settings`, free-form TOML (RFC 42) declaring every table and key timber's reader takes, each `nullOr` its TOML type with no default: `store` (`layout`, `registry`), `landing` (`sluice`, `branch`, each a table holding `remote`), `ledger` (`git_ref` holding `remote`, and `store`, a table declaring nothing), `signing` (`signer`, `key`, `kms`), `gate` (`publish`, a table declaring nothing, and `job`), `trust`, each signer by its name a table of its one key, and `credentials`, each credential by its name the path of the file that holds it. Each description says what the key binds, what holds where it is unset, and its clause, in the self-hosting guide's words. Types and nothing finer: that a seam's table names one profile, that `kms` stands alone, that a registry's name has a `/`, and every given binding are timber's, refused or given at its read, naming the table.
- **What is unset is left out, and an empty table set is written.** Before rendering, every null at any depth is taken out and nothing else: `branch = { }`, `git_ref = { }`, `store = { }` and `publish = { }` each bind their profile with no options (record 0013). `settings = { }` renders the header alone, and a key the module does not declare passes to the file for timber to judge.
- **A credential and a key are named by their paths, outside the store.** With the module enabled, `settings.signing.key` and each `settings.credentials.<name>` must begin `/` or `~/`, as timber reads every path of the file, and must not begin with the store directory. Each failure is its own message, naming the option and saying the store is read by every user; a Nix path value fails `types.str` before anything copies it. The module names the path and never reads, copies or checks the file, which is the host's (45, 64; record 0033; core.21). `[signing] kms` and `[trust]` hold a key's ARN and a public key, no secret, and are asserted nothing.
- **The file is rendered at evaluation.** `nix/modules/toml.nix` is sluice's renderer at 7ce112b4, its header line `# Written by timber's flake module from services.timber.settings; a change goes there.` and its failure naming `services.timber.settings.<path>`: keys before tables, each sorted by name; a table holding only tables named by theirs; a table holding nothing by its header alone; anything but a string, a boolean, an integer, a list of strings, a table or a list of tables failing with its path. The file is `pkgs.writeText "timber-config.toml"` of the text, so the gate compares the text without building it.
- **The activation links the file for the user who runs timber.** `nix/modules/activate.sh link <file>` is sluice's for `~/.config/timber/config.toml`: a link to the file there already, nothing; another link, replaced; a file or folder that is no link, moved once to `config.toml.before-nix`, both paths named; that path taken already, neither changed, both named, exit 1. It links the file alone, never `~/.config/timber/`, which may hold a host key the file names. On nix-darwin it runs in `postActivation` as the primary user under their home, a primary user with no `users.users.<user>.home` failing evaluation naming that option; on NixOS in `system.userActivationScripts.timber` for `services.timber.user` alone, a user `users.users` declares as neither a normal nor a system user failing evaluation naming both. `|| true` on both: a link that fails says why and stops nothing else of the activation.
- **The package, and nothing else on the host.** `environment.systemPackages` holds the package where it is not null. The module adds no launchd agent or daemon and no systemd unit, so no `timber serve`, which the first asker that finds none starts (114, core.36); no file under `/etc`, no user and no lingering; nothing under the data directory, where timber makes its given layout and host key (core.54); and no other tool's file (boomdrive core.18).
- **The checks: a moon project `nix`.** `lint` runs statix over `flake.nix` and `nix/`; `typecheck` and `test` run `nix/check.sh`, which evaluates `nix/tests` with `TIMBER_FLAKE_NIX`, offline and read-only against `dummy://?store=/timber-check/store`, its configuration, caches and state a scratch folder's, reading the flake's inputs where the devenv shell fetched them (`TIMBER_FLAKE_INPUTS`, from `nix/inputs.nix`, sluice's); `test` also runs `nix/tests/activate.sh` in scratch homes. Each failure is one line, `nix: <case>: <what>`, and every case runs. devenv.nix pins nix 2.34.8, reached by its path and kept off `PATH` so the tools layer keeps the host's nix, and statix 0.5.8-unstable-2026-07-17, both asserted (core.26). Each task's inputs are what it reads: the flake, the lock, `nix/`, devenv's files, and the package's `Cargo.toml`, `Cargo.lock` and `.prototools`, with `crates/` for `typecheck`. The format is `root:format`'s, and `treefmt.nix` excludes `nix/tests/files/**`, the rendered files the cases compare byte for byte (core.25). No check needs a credential or the network (core.38).
- **timber reads what the module writes.** The unit test `the_modules_files_are_read_as_written` reads `nix/tests/files/laptop.toml` and `fleet.toml` through `bindings::read`: between them every key the module declares but `credentials`, each seam's two profiles split across them. `nix/tests/files/credentials.toml` is compared by the flake's cases and read by no test here: the reader of `[credentials]` and its test are the change timber-deploys-a-datasets-dash0-dashboards's.

Not taken:

- **Option 2.** An option named otherwise than the file's key, which boomdrive core.46 rules out.
- **The given bindings as the options' defaults.** A table the file names binds exactly what it names, and the given landing and ledger differ per repository (118); a module that wrote them would make every table written and change what it binds.
- **A closed set of options holding timber's rules.** Every rule of the reader would live twice.
- **sluice's prune unchanged,** which drops a table left with no key, so `branch = { }` would bind the given landing in its place.
- **A credential's path refused unless it begins `/`,** as 118's words "the absolute path" read alone: timber's reader takes `~/` in every path of the file, and the module refuses only what may be a secret's text or lies in the store.
- **Refusing every key named `key`, `token`, `secret` or `password`,** as Boomdrive's module does, which would refuse timber's own `key` path; and a secrets integration of the module's own.
- **Importing sluice's renderer from its flake,** which would make timber's flake take sluice's as an input for one file.
- **A file written in place,** where a link names the generation that wrote it; **a flag or variable naming the file,** which every caller would pass; **linking at a non-default `XDG_CONFIG_HOME`,** which the activation, outside the user's session, cannot read.
- **`pkgs.nix` on the shell's `PATH`,** as sluice's shell has it, which would hand the tools layer's Nix cache and fleet tests a nix client other than the host's; **a build of the file or a system in the gate,** where the sandbox gives no daemon and a darwin system cannot be built on Linux.
- **nix-darwin's newest commit in the lock,** which may ask for a newer nixpkgs than timber's; sluice's revision evaluates against it.
- **Option 3.** A nix-darwin or NixOS host need not run home-manager, and the family's modules are system modules.
- **Option 4.** boomdrive record 0023 rejects it as its option 3: no module writes another tool's file.

### Consequences

- Good: a nix-darwin or NixOS host writes timber's bindings, a credential's path among them, as `services.timber.settings`, from timber's own flake, with no Boomdrive, and no secret reaches the store by the module.
- Good: the gate shows the module's text, its links and that timber reads what it writes, offline and with no store.
- Neutral: until the change timber-deploys-a-datasets-dash0-dashboards lands, timber refuses a file holding `[credentials]`; both changes land in one bolt, so no release carries the module without the reader.
- Neutral: the renderer and the link are copies of sluice's; a fix to one is not a fix to the other, and each file's opening comment names the revision it was taken from.
- Neutral: a host that enables the module while another writer still writes `~/.config/timber/config.toml` has two writers, the last activation winning, until it drops the other.
- Neutral: Boomdrive's set taking the module, setting `services.timber.package` and `user`, and dropping `services.boomdrive.timber.package` wait on a release that carries it, and are agentplot/boomdrive's.
- Rule core.76 says it; rules core.1 and core.25 name the flake's `nix/`.
